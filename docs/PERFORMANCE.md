# Packaged performance evidence

Local measurements from October 11, 2026 use the Windows x64 preview on an Intel Core i7-14700F (28 logical CPUs), approximately 32 GiB RAM and Windows build 26200. These are engineering samples, not certification for all displays, courses, clients or hardware.

## Latency and drawing

`npm run measure:performance` uses the packaged executable in `release/win-unpacked` by default. Set `CCC_EXECUTABLE` to test a specific installed executable. It creates isolated app data and a fixture provider home, sends native helper events, takes a real shot, and records `work/performance/result.json`. It never enrolls live hooks or reads subscription credentials.

| Measurement | Latest local sample | Scope |
| --- | --- | --- |
| Warm helper launch/write/exit | 60 samples; p95 19.50 ms; maximum 20.74 ms | Five warmups excluded; native broker available |
| Click to observed acknowledged shot | 29.00 ms | Includes Playwright input and polling overhead |
| Renderer RAF scheduling | 1,080 intervals; mean 180 fps; p95 5.70 ms; maximum 6.40 ms | Six seconds on this high-refresh desktop; not presented-frame tracing |
| Actual canvas draw starts | 404 draws; p95 interval 11.20 ms; maximum 12.00 ms | During the same shot sample; no interval above 33.4 ms |
| Show after configured one-second delay | 12 samples; maximum 16.61 ms beyond delay | Warm renderer; each automatic show reported unfocused |
| Normal stop/attention to hidden | 8 samples; maximum 14.63 ms | First post-acceptance state publication to native hide event |
| Stalled renderer stop/attention to hidden | 4 samples; maximum 186.81 ms | Injected 450 ms renderer JS stall; same main-process timing clock |

State publication occurs shortly after registry acceptance, so a small amount of synchronous acceptance work precedes the recorded latency origin. The benchmark avoids external polling time in hide measurements but does not instrument the exact first instruction of acceptance. The 200 ms requirement still needs broader I/O and hardware checks. Warm show timing does not cover a parked renderer's recreation or cold process startup.

## Offline behavior

Chromium net logging starts at process launch and flushes on normal exit. The latest benchmark recorded **zero HTTP or WebSocket URLs** during startup, a real shot, helper activity and twelve show/hide cycles. Raw trace data stays in its temporary fixture profile. This is Chromium instrumentation, not OS-wide packet capture; it does not cover intentional documentation links, provider clients, every operating system or every failure mode.

## Hidden resources

`npm run measure:resources` samples a hidden window, waits for its renderer to park, measures counters, explicitly reopens, compares the exact saved round, and checks rendered turf/background pixels. Use `CCC_EXECUTABLE` for packaged results. The memory sum includes both Electron processes and the owned native Go hook helper. Earlier Electron-only readings omitted that helper and must not be described as complete application totals. Shared pages can appear in more than one working set; keep the same summed metric for the initial 200 MiB budget.

`--software --no-software-rasterizer` is a test-only command-line graphics experiment. Its packaged measurement was 199.41 MiB for Electron plus 9.48 MiB for the helper, **208.88 MiB total**, with exact save and canvas recovery. The earlier development measurement of 202.66 MiB omitted the helper. Neither establishes the memory target. Production graphics defaults remain unchanged.

The refreshed default packaged measurement is **254.30 MiB total** (244.73 MiB Electron plus 9.57 MiB helper). Electron CPU measured 0.0757%; the helper accumulated no measurable CPU during the idle interval. Exact saved-state and canvas recovery passed. This is a local parked sample, not a long-duration resource ceiling.

Resource JSON reports Electron CPU and the helper's measured idle CPU separately. Helper CPU is expressed as a percentage of one logical core over the parked sampling interval. Do not silently combine differing CPU normalization conventions or substitute private bytes for summed working sets.

## Remaining gates

A test-only launch requested Chromium's `NetworkServiceInProcess` feature alongside software rendering/no software rasterizer. It measured **210.11 MiB summed working set**, including the helper; a Utility process still remained. Exact save and rendered-canvas recovery passed. This did not establish that the requested network mode took effect or improve the memory budget. It is not an app default. [Chromium's own notes](https://chromium.googlesource.com/chromium/src/+/main/services/network/README.md) prefer a separate network process for isolation and crash recovery; current source/flag support must not be inferred from the flag's presence on the command line. Evidence: `work/resources/software-no-rasterizer-in-process-network.json`.

An additional test-only `--software --no-software-rasterizer --compact-v8` experiment constrained V8 to a 64 MiB old-space heap with size optimization. It measured **211.43 MiB summed working set**, including the native helper. Exact save and canvas reopen checks passed, but it showed no useful improvement over the 208.88 MiB graphics experiment. The compact heap is not an app default. Evidence: `work/resources/software-no-rasterizer-compact-v8.json`.

The hidden-memory target remains unmet. Sustained compositor frame presentation across all nine holes, additional display scales, lower-end hardware, physical sleep/wake, cold/parked show latency, actual provider permission flows and OS-level network capture remain open. Measurements do not imply that untested client surfaces or the unsigned installer are production-ready.

## Parked automatic lifecycle

Each restored the exact acknowledged round and accepted a real drag shot. Stop/interruption hid within 13.33 ms and 13.96 ms of broker stdout event ingress. Attention arriving during recreation canceled the pending show; the recreated window never showed and the saved state remained exact. Timing uses the main-process monotonic clock at broker stdout ingress before desktop processing, so this origin differs from the earlier warm benchmark's first publication. These are two local cold-renderer samples, not broad hardware certification or cold application startup.

This separate gameplay fixture confirms the memory target remains unmet; it does not replace the earlier resource benchmark or establish a maximum. No working-set trimming, private-byte substitution, graphics default change or isolation reduction was used. Further memory work must address the retained Chromium processes while preserving the Electron desktop experience, reliable hooks and fast inactive reopening.

It collects three cold samples, opens practice, dispatches a real drag and waits for the acknowledged ball to settle, hides normally, waits for the production renderer parking timer, and collects three parked samples. Reopening must preserve exact round state with a nondecreasing save revision and produce turf/cyan canvas pixels. Sandbox, context isolation and web security remain enabled, and Node integration remains disabled. Reopen-to-restored-bridge timing is approximately 87 ms in each run, not a physical presented-frame or automatic-show measurement.

Windows counters cover the spawned app and recursively discovered descendants, **including the Go helper and its console host**. Shared pages may be counted more than once. This wider scope explains part of the difference from prior Electron-plus-helper measurements; do not interpret it as a product memory regression or improvement.
